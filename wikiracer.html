Project Overview

This project implements the Wikiracer game, a navigation challenge based on Wikipedia. Wikiracing is a game in which players attempt to move from one Wikipedia article to another using only internal Wikipedia links. All allowed links follow the format /wiki/Page_Name, ensuring that navigation stays strictly within Wikipedia.

In this project, we are given two Wikipedia articles: a start page and a goal page. The task is to reach the goal page starting from the source page by clicking only the links found inside the articles we visit.

🧩
Wikipedia as a Graph

To solve this problem algorithmically, Wikipedia is modeled as a directed graph where Wikipedia pages are nodes and hyperlinks are edges between pages.

Bidirectional
A ↔ B

Page A links to Page B, and Page B links back to Page A.

One-way (A → B)
A → B

Page A links to Page B, but Page B does not link back.

One-way (B → A)
B → A

Page B links to Page A, but Page A does not link back.

Because hyperlinks are not guaranteed to be reciprocal, directionality plays a critical role in how graph search algorithms behave.

⚡
Project Goal: Efficiency

The main goal of the project is to find a path between two Wikipedia pages as efficiently as possible.

Efficiency is measured in two ways:

  • Number of links (clicks)
    Each click represents moving from one page to another via a hyperlink. Fewer clicks correspond to a shorter path.

  • Number of page downloads (resources)
    Each time a page is accessed, its HTML must be downloaded. Downloads are computationally expensive and dominate runtime.

While traditional graph algorithms focus on minimizing clicks, the final Wikiracer implementation prioritizes minimizing page downloads, even if the resulting path contains more links. This reflects the real-world constraint that network requests are far more costly than local computation.

Solutions

The project is approached using three different algorithms: Breadth-First Search (BFS), Depth-First Search (DFS), and a Custom Asynchronous BFS Wikiracer. While BFS and DFS serve as foundational baselines for understanding graph traversal and path discovery, the third algorithm is the most critical component of the project.

  • Breadth-First Search (BFS)
    BFS explores Wikipedia level by level, guaranteeing the shortest path in terms of clicks and avoiding deep, misleading navigation paths early on.

  • Depth-First Search (DFS)
    DFS commits to long, narrow link chains without context, often diving into irrelevant topics and wasting many page downloads before discovering whether a path toward the goal even exists.

  • Custom Asynchronous BFS Wikiracer
    The third and most important algorithm is a custom Asynchronous Breadth-First Search. Instead of expanding the graph from only the source page, the algorithm searches simultaneously from both the source and the target page. However, a path discovered from the target to the source does not automatically imply a valid solution, since Wikipedia links are directed and the goal is to find a path from source to target.

Efficiency strategies used by the custom Wikiracer:

  1. Take the Highway Strategy
    Prioritizes highly connected and well-known Wikipedia hub pages that statistically increase the likelihood of quickly reaching the target.

  2. Semantic Link Similarity Detection
    Increases priority for semantically related links by comparing page names for shared words or meaningful substrings (e.g. Germany_technology and German_language),under the assumption that semantically related pages are more likely to converge.

  3. Search Depth Limitation
    Most Wikipedia pages can be connected within a small number of links (often under six). To prevent the algorithm from exploring deep, unproductive paths and entering large loops, a maximum exploration depth is enforced.
Note: To ensure consistent results, the project was developed and tested using a frozen snapshot of Wikipedia. The final solution passed over 150 automated tests, evaluating both correctness and efficiency.
